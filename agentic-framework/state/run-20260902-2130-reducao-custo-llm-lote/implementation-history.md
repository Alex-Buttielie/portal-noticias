# Implementation History — 20260902-2130-reducao-custo-llm-lote

## Iteracao 1 — 2026-09-02 — orchestrator agindo como executor

**Restricao central respeitada:** `executar_ingestao` continua chamando o provider com CADA item de forma INDEPENDENTE (nunca um resumo combinado compartilhado entre itens de fontes diferentes) — essa e a correcao anti-misattribution do Finding 1 (3a passada, code-review-contract.md run 20260902-0727-ingestao-noticias) e NAO foi revertida. A reducao de custo veio de agrupar VARIAS chamadas independentes numa unica requisicao HTTP, nao de combinar conteudo.

**`providers/summarization.py`:**
- `SummarizationProvider.resumir_e_classificar_em_lote(itens) -> list[ResultadoResumo]` adicionado como metodo NAO-abstrato na classe base, com implementacao padrao = `[self.resumir_e_classificar([item]) for item in itens]`. Isso preserva 100% o comportamento de TODOS os dubles de teste ja existentes (nenhum sobrescreve este metodo), sem exigir alterar nenhum mock.
- `LLMHttpSummarizationProvider` sobrescreve com uma chamada HTTP real: `_montar_prompt_lote` numera as noticias, `_interpretar_resposta_lote` espera uma lista JSON com objetos `{"id", "resumo", "categoria", "urgente"}`, mapeados por `id` (nunca por posicao). Um id ausente/invalido vira `ResultadoResumo(resumo="")` SO para aquele item (forca revisao humana em `services/ingestao.py`, mesmo tratamento ja existente para qualquer resumo nao confiavel), sem afetar os demais itens do lote. Resposta que nao e uma lista JSON valida levanta `SummarizationProviderError` para o lote inteiro.
- `_chamar_api` ganhou um parametro opcional `max_tokens` (None por padrao — preserva o comportamento historico de `resumir_e_classificar`, que nunca passa esse valor). `resumir_e_classificar_em_lote` sempre passa um valor calculado (`max_tokens_por_item * tamanho_do_lote`).
- Novos settings: `CATALOGO_NOTICIAS_LLM_TAMANHO_LOTE` (padrao 10) e `CATALOGO_NOTICIAS_LLM_MAX_TOKENS_POR_ITEM` (padrao 220, gap real: nenhum teto de tokens de resposta existia antes).

**`services/ingestao.py::executar_ingestao`:** reestruturado em 3 fases dentro da mesma funcao (nenhuma mudanca em `_persistir_grupo`/`_persistir_grupo_mesclado`/dedup/`_itens_recentes_persistidos`):
1. Itera `grupos` como antes, decidindo `itens_novos_do_grupo`/`news_items_existentes_do_grupo` por grupo (logica identica a antes) — mas em vez de resumir inline, guarda em `grupos_processados` e acumula todos os itens novos (de TODOS os grupos) numa lista flat `todos_itens_novos`.
2. `todos_itens_novos` e cortado em lotes de `CATALOGO_NOTICIAS_LLM_TAMANHO_LOTE`, cada lote passado a `resumir_e_classificar_em_lote`. Defesa adicional: se o provider devolver uma lista de tamanho DIFERENTE do lote enviado, o lote INTEIRO e descartado para revisao humana (nunca faz `zip` desalinhado, que arriscaria atribuir o resumo de um item a outro). Resultado mapeado por `url_fonte_original` (unico por item numa mesma execucao).
3. Persistencia grupo a grupo, EXATAMENTE como antes, so que buscando cada resultado no dicionario pre-calculado em vez de chamar o provider inline.
